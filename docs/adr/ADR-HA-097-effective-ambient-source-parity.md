# ADR-HA-097: Effective Ambient Source Parity

**Date**: 2026-05-22  
**Status**: APPROVED

## Context

Indoor lux sensors can be contaminated by lights in the same location. Topomation
lets the Ambient inspector select which local `light.*` entities can contaminate
a location's direct lux sensor. When any selected light is on, Topomation skips
that local sensor and falls back to inherited lux or sun state.

The previous managed Lighting rule compiler did not follow that same source
priority. Generated Home Assistant automations selected one lux source at save
time: local lux if configured, inherited lux only when no local sensor existed,
and sun only when no lux source existed. That meant the Ambient page could show
"local lux ignored, using parent/sun" while the generated rule still watched the
contaminated local sensor. In the opposite direction, naively requiring all
local lights to be off before any bright rule can run would prevent sunrise or
clean parent lux from turning lights off while the local sensor is contaminated.

## Decision

Ambient reading diagnostics and generated managed Lighting automations must use
the same effective-source priority for every topology location, including
structural hosts:

1. Use the location's explicitly configured local lux sensor when it is usable.
   A same-location lux candidate is not an effective local source while the
   location is configured to inherit from parent.
2. When any selected local lux-contaminating `light.*` entity is `on`, treat the
   local lux sensor as unusable.
3. If the local lux sensor is unusable and inherited ambient is enabled, use the
   first usable ancestor lux sensor.
4. If the local lux sensor is unusable, no inherited lux source exists, and sun
   fallback is enabled, use `sun.sun` as the strict sunrise/sunset fallback.
5. Only `light.*` entities participate in local lux contamination. Switches,
   helpers, non-light devices, and descendant-location lights do not count in
   this contract.

Generated managed Lighting automations must wake from every source that can
become effective under this priority. Their conditions must then enforce the
priority order so a contaminated local lux reading cannot pass just because it
crossed the dark/bright threshold.

## Rationale

1. The Ambient inspector and managed rules should not explain different ambient
   realities for the same location.
2. Parent/outdoor lux and sunrise/sunset are the only useful bright signals while
   an indoor sensor is illuminated by the room's own lights.
3. Restricting contamination to direct `light.*` entities keeps the model simple
   and predictable. Users who need broader semantics can create a light group in
   Home Assistant and assign that light entity to the location.
4. Generated HA automations still remain inspectable: triggers describe possible
   wake sources, while conditions encode the effective-source priority.

## Consequences

- Managed rules generated by older metadata versions must be rebuilt.
- Ambient-only bright rules can turn lights off at sunrise when local lux is
  contaminated and no parent lux sensor exists.
- Ambient-only bright/dark rules may include a source-priority condition even
  when the rule's same-family ambient condition is otherwise `any`; this is not
  a redundant self-guard, it is source arbitration.
- The Ambient inspector must explain which local lights are considered and which
  source is currently effective.

## Validation Requirements

1. Backend tests prove local lux is used when clean.
2. Backend tests prove contaminated local lux falls back to inherited lux.
3. Backend tests prove contaminated local lux falls back to `sun.sun` when no
   inherited lux exists.
4. Trigger-shape tests prove managed Lighting rules wake from parent lux or sun
   fallback when those sources can become effective.
5. UI tests or live validation confirm the Ambient tab explains the effective
   source priority and names ignored local lights.
