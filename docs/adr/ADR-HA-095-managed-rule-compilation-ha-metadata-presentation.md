# ADR-HA-095: Managed Rule Compilation, HA Metadata, and Presentation Invariants

**Date**: 2026-05-07  
**Status**: ✅ APPROVED

## Context

Topomation-managed automations are generated from a product-level rule editor
and then written as Home Assistant automations. Users may inspect and debug the
generated rules in Home Assistant's native automation UI, so the generated
automation must be understandable, executable, and organized in the same places
Home Assistant users expect.

Live inspection showed managed Lighting rules that compiled into contradictory
or redundant HA automation shapes. Example failure modes:

1. `on_bright` trigger plus `bright` condition, yielding "when illuminance is
   above threshold" and "only if illuminance is above threshold." This is
   redundant and obscures the rule's intent.
2. `on_bright` trigger plus `dark` condition, yielding "when illuminance is
   above bright threshold" and "only if illuminance is below dark threshold."
   This is logically impossible at the moment the rule wakes.

Lighting exposed the issue first because it has both occupancy and ambient
trigger families. The underlying risk applies to every managed-action tab:
stale draft fields, trigger changes, target-domain changes, or metadata rebuilds
must not produce automations whose triggers and generated guards contradict each
other.

Separately, generated automations need better HA presentation. Topomation knows
which topology row a rule was authored from, which HA area should own that rule,
and enough about the target domain/action to choose a more meaningful default
icon than a generic automation icon.

## Decision

Managed rules compile through a normalized intermediate model before Home
Assistant YAML/config is generated.

1. The backend compiler is the source of truth for validity. Frontend controls
   may guide users, but backend creation/rebuild must reject or normalize
   impossible rule combinations.
2. No managed rule may compile into a HA automation whose trigger and generated
   condition are mutually exclusive.
3. Same-family self-guards are not generated by default:
   - `on_bright` does not also emit an ambient `bright` condition.
   - `on_dark` does not also emit an ambient `dark` condition.
   - `on_occupied` does not also emit a must-be-occupied condition.
   - `on_vacant` does not also emit a must-be-vacant condition.
4. Opposite same-family guards are invalid:
   - `on_bright` plus `dark`
   - `on_dark` plus `bright`
   - `on_occupied` plus must-be-vacant
   - `on_vacant` plus must-be-occupied
5. Cross-family guards remain valid:
   - occupancy trigger plus ambient guard, such as "when occupied, only if dark"
   - ambient trigger plus occupancy guard, such as "when bright, only if vacant"
6. Lighting keeps its two trigger families: occupancy edge and ambient edge.
   It may include at most one trigger from each family.
7. Appliances, Media, HVAC, and Vacuum remain occupancy-edge tabs unless a
   later ADR adds more trigger families. They must not persist ambient trigger
   or ambient condition semantics.
8. Rule compilation owns action-domain normalization. Changing a target or tab
   must re-evaluate trigger defaults, action defaults, action data, and guards
   together rather than preserving stale incompatible fields.
9. Every managed automation is assigned to an HA area when saved or rebuilt:
   - room-like `area` / `subarea` rows use the row's direct `ha_area_id`
   - structural hosts (`property`, `building`, `grounds`, `floor`) use the
     host's managed-shadow HA area
   - if a user-authored rule cannot resolve a valid HA area, saving fails with
     a diagnostic error rather than silently creating an unscoped automation
10. Every managed automation keeps the existing Topomation category and exactly
    one Topomation label. Trigger semantics stay in the alias and embedded
    metadata, not in trigger-specific HA labels.
11. Every managed automation receives a generated icon derived from rule tab,
    target domain, and primary action. The icon is Topomation-owned metadata
    unless a future ADR adds user-controlled automation icons.
12. Managed automation metadata must version this compiler contract. Existing
    managed rules are rebuilt in place during the next release migration so HA
    automations converge to the new invariants without manual recreation.

## Initial Icon Policy

Generated icons are defaults, not a new customization surface.

1. Lighting:
   - `mdi:lightbulb-group` for general lighting rules
   - `mdi:lightbulb-off` for primary turn-off rules
2. Appliances:
   - `mdi:fan` for `fan.*`
   - `mdi:power-plug` or a device-class-specific icon for `switch.*`
3. Media:
   - `mdi:speaker-wireless` for general player rules
   - action-specific icons such as play, pause, mute, or volume when clear
4. HVAC:
   - `mdi:hvac`, `mdi:fan`, or `mdi:thermostat` depending on target/action
5. Vacuum:
   - `mdi:robot-vacuum` for start/cleaning rules
   - action-specific variants for pause or dock when clear

If HA does not expose a durable automation-icon registry field in the supported
runtime, the compiler may defer icon persistence while still documenting and
testing the icon-selection function used by Topomation's own UI surfaces.

## Rationale

1. Generated automations are executable artifacts, not just UI summaries. They
   must be correct even when inspected, edited around, rebuilt, or migrated.
2. HA automations wake on edges and evaluate conditions afterward. A condition
   that contradicts the edge makes the rule inert; a condition that repeats the
   edge adds noise without adding policy.
3. Cross-family guards are meaningful because they describe independent state:
   ambient state can guard occupancy edges, and occupancy state can guard
   ambient edges.
4. Centralizing rule compilation prevents stale UI draft fields from leaking
   into saved automations.
5. Assigning HA area/category/label metadata makes managed automations discoverable
   in Home Assistant's native Automations & scenes views.
6. Structural hosts already use managed shadow areas for HA interoperability;
   generated rules should follow the same ownership model.
7. Domain/action-specific icons make generated rules easier to scan without
   adding a manual customization workflow too early.
8. Versioned rebuild keeps existing installations from carrying broken rule
   shapes indefinitely.

## Consequences

- ✅ Managed rules become harder to compile into inert or contradictory HA
  automations.
- ✅ Lighting rule semantics become clearer: trigger families wake the rule;
  only cross-family conditions guard it.
- ✅ Non-light tabs stay simple and explicitly occupancy-only.
- ✅ HA area assignment becomes mandatory and predictable.
- ✅ HA automation lists become easier to scan by area, category, label, and icon.
- ✅ Future managed-rule tabs have a compiler checklist instead of copying
  ad hoc behavior.
- ⚠️ Some existing rules will change shape during metadata-version rebuild,
  especially ambient-trigger Lighting rules that currently emit redundant
  ambient conditions.
- ⚠️ Save failures for missing HA area/shadow metadata are stricter than the
  previous best-effort grouping behavior.
- ⚠️ Icon persistence may depend on HA registry support; if unsupported,
  Topomation-owned icon selection must remain internal until a durable HA path
  exists.

## Validation Requirements

Implementation of this ADR must include:

1. A compiler truth table for valid trigger/guard combinations.
2. Backend tests rejecting or normalizing impossible combinations:
   - `on_bright` plus `dark`
   - `on_dark` plus `bright`
   - `on_occupied` plus must-be-vacant
   - `on_vacant` plus must-be-occupied
3. Backend tests proving self-guards are stripped or not emitted by default.
4. Tests that Appliances, Media, HVAC, and Vacuum saves cannot persist ambient
   trigger or ambient guard semantics.
5. Tests that room-like rules get direct HA area assignment and structural-host
   rules get managed-shadow HA area assignment.
6. Tests for generated icon selection, even if icon persistence is deferred by
   HA runtime limitations.
7. A metadata-version migration/rebuild test proving existing managed rules are
   rewritten in place.
8. Live HA validation that inspects the generated automation config and HA
   entity registry metadata, not only the Topomation panel state.

## Alternatives Considered

- Keep current UI-driven field normalization: rejected because stale draft
  fields can still produce contradictory backend artifacts.
- Allow redundant self-guards because HA accepts them: rejected because they
  confuse debugging and hide the distinction between wake events and policy
  guards.
- Silently save unscoped automations when area resolution fails: rejected
  because Topomation knows the authoring location and users expect the rule to
  appear there in HA.
- Add user-editable icons now: rejected for this ADR. Generated defaults solve
  the scanning problem; customization needs separate ownership metadata and UI.
- Split this into separate ADRs for compiler, area, and icons: rejected because
  the user-visible problem is one generated-automation contract. Implementation
  may still land in separate slices.
